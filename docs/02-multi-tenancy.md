# Фаза 2 — Multi-tenancy изолация

## Цел

Всяка организация (кредитен посредник) да работи с напълно изолирани данни — така
че организация А да не може дори случайно да види данни на организация Б. Това е
критично при лични и финансови данни.

## Какво включва

- **Schema-per-tenant** архитектура: всяка организация има собствен набор от
  таблици в PostgreSQL. Глобалните таблици (`Tenant`, `User`) живеят в обща
  `public` schema.
- Динамично създаване на нова организация с нейна schema.
- Request-scoped изолация през `AsyncLocalStorage` — сърцето на фазата.

### Endpoints

| Метод | Път | Описание |
|---|---|---|
| POST | `/tenants` | Създава организация с нова schema (само ADMIN) |

## Ключови решения (и защо)

### Отделна schema за всяка организация
Данните на организация А физически стоят на различно място от тези на Б.
`Tenant` и `User` са в `public`, защото са глобални (един потребител принадлежи
на една организация).

**Защо schema-per-tenant, а не един общ филтър по `tenantId`:** по-силна изолация
— грешка в един ред код не може да „изтече" данни между организации, защото те
физически са в различни schemas.

### Изолация при паралелни заявки (AsyncLocalStorage) — най-важното тук
Сървърът обслужва много заявки едновременно. Ако „текущата организация" се пази
като обикновена променлива в услугата, две едновременни заявки от различни
организации биха се презаписали взаимно → изтичане на данни.

**Решение:** `TenantContextService` обвива Node.js механизма `AsyncLocalStorage`.
`TenantMiddleware` при всяка заявка изважда организацията от JWT токена и обвива
останалата част от заявката в контекст `{ tenantId, schemaName }`. Целият
downstream код на тази заявка автоматично вижда своята организация, без глобален
mutable state.

`PrismaService` има два достъпа:
- `publicDb` — за `Tenant`/`User` (винаги `public`).
- `tenantDb` — чете schema-та от контекста при всеки достъп; ако няма активен
  контекст → хвърля грешка (защита срещу достъп извън заявка).

Клиентите по schema се кешират (per-schema connection pooling).

### Provisioning на нова организация
`TenantsService.createTenant` създава `Tenant` запис + нова PostgreSQL schema, в
която прилага програмно всички миграции (в транзакция). Локалните копия на
`User`/`Tenant` се дропват от tenant schema-та — те живеят само в `public`.

## Правила и валидации

- Имената на schema минават през строг шаблон (защита срещу SQL injection).
- Достъп до tenant-скопирана таблица без активен контекст → `500` (програмна грешка).
- Невалиден/неактивен tenant в токена → `401`.

## Тестове

- **Concurrency тест (критичен):** две паралелни операции с различен контекст и
  разменени изкуствени забавяния — всяка вижда своята schema, не на другата.
- Контекстът не „изтича" извън заявката.
- Middleware обвива заявката в правилния контекст; публичните маршрути се пропускат.

## Как да се провери

```bash
# Създай организация (като ADMIN)
curl -X POST http://localhost:3000/tenants \
  -H "Authorization: Bearer <ADMIN_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"Нова Фирма ЕООД"}'
```
Отговорът връща `schemaName`; в базата се появява нова schema с всички таблици.
Потребител от друга организация вижда 0 записа от чуждата.

## Оперативна бележка

Нова миграция се прилага автоматично само към `public`. Съществуващите tenant
schemas се мигрират ръчно (със `search_path`). Изключение: миграции по `User`
(напр. добавяне на колона) са само за `public`, защото `User` не съществува в
tenant schemas.
