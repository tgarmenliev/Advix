# Фаза 5 — Кредитна заявка и workflow

## Цел

Централният обект в системата. На кредитната заявка се крепи всичко — тя минава
през строго дефиниран път от статуси, от първи контакт до отпускане. Това е
най-критичната фаза.

## Какво включва

- CRUD за заявки, с филтри и странициране.
- **Workflow state machine** — позволените преходи между статуси.
- Права по роля при създаване, преходи и достъп (видимост).
- Назначаване/прехвърляне на консултант, смяна на тип, връщане за корекция.
- Управление на съдлъжници до финализиране и **размяна на роли** (flip).

### Endpoints

| Метод | Път | Описание |
|---|---|---|
| POST/GET | `/loan-applications` | Създава / списък (с видимост по роля) |
| GET/PATCH | `/loan-applications/:id` | Детайл / редакция на базови полета |
| PATCH | `/loan-applications/:id/assign` | Назначава/прехвърля консултант (ADMIN) |
| PATCH | `/loan-applications/:id/change-type` | Смяна на типа кредит (ADMIN) |
| POST | `/loan-applications/:id/transition` | Смяна на статус |
| POST | `/loan-applications/:id/flip-borrower` | Размяна основен клиент ↔ съдлъжник |

## Ключови решения (и защо)

### Workflow като конфигурация, не като код
Статусите и позволените преходи са описани като структура (карта), не като
разхвърляни `if`-ове. Невалиден преход (напр. директно от `NEW` към
`READY_FOR_BANK`) → `400` с ясно съобщение кои преходи са позволени.

### Задължителна проверка преди банка
Преди `READY_FOR_BANK` системата изисква попълнени `client.egn`, `netSalary`,
`contractType`, `gdprConsentAt`, както и `amount` и `termMonths` на заявката. При
липса → `400` с точен списък на липсващите полета.

### Хлабаво създаване + партньорски поток
За нова заявка стигат `clientId`, `loanType`, `amount`. Партньор Модел А въвежда
**лийд без назначен консултант** (`consultantId` е празен); ADMIN после назначава
консултант през `/assign`. Затова `consultantId` и `termMonths` са опционални при
създаване.

### Видимост по роля (сигурност на данните)
- **ADMIN** вижда всички заявки в организацията.
- **CONSULTANT** и **PARTNER_B/C** виждат своите.
- **PARTNER_A** вижда само своите лийдове и то в **ограничен изглед** (без пълното
  досие — вътрешни бележки, ЕГН и т.н. не се показват).

Всяка мутираща операция проверява собственост (чужд достъп → `403`).

### ADMIN връщане за корекция
ADMIN може да върне заявка към `COLLECTING_INFO` от **всеки нетерминален статус**
(извън обичайните преходи) — напр. ако банката вече гледа заявката, но е излязла
грешка в данните.

### Смяна на типа кредит — рядък краен случай
Само ADMIN, само преди финализиране (`COMPLETED`/`REJECTED_BY_CLIENT`), през
отделен endpoint. От общия update `loanType` е премахнат — не се сменя случайно.

### Flip: основен клиент ↔ съдлъжник
Бизнес нужда: понякога съдлъжникът трябва да стане основен кредитоискател.
Понеже `Client` и `FamilyMember` са различни таблици, flip-ът:
- промотира съдлъжника до `Client` с **дедупликация по ЕГН** (ако човекът вече е
  клиент — преизползва записа, не дублира);
- демотира стария клиент до съдлъжник под новия;
- разменя връзките и пренасочва заявката.

Всичко в **една транзакция** и е **обратимо**.

## Правила и валидации

- Вътрешни бележки (`internalNotes`) пишат само ADMIN/CONSULTANT/PARTNER_B/C.
- Съдлъжници се добавят/махат само докато заявката не е **финализирана**
  (`DISBURSED`/`COMPLETED`).
- Flip само за лице, включено в заявката, и само преди финализиране.
- `CLIENT` не сменя бизнес статуси; `PARTNER_A` не изпраща към банки.

> **Две различни понятия за „край":** *терминален* (`COMPLETED`,
> `REJECTED_BY_CLIENT`) — за смяна на тип и ADMIN връщане; *финализиран*
> (`DISBURSED`, `COMPLETED`) — за заключване на съдлъжници и flip.

## Тестове

- Всеки валиден преход минава; невалиден → `400`.
- `READY_FOR_BANK` без данни → точен списък липсващи полета.
- Права: `CLIENT` не сменя статус; `PARTNER_A/B` не изпращат към банки.
- Видимост: консултант вижда своите; PARTNER_A — ограничен изглед.
- Flip: размяна коректна, без дубликат по ЕГН, обратим; блокиран след финализиране.

## Как да се провери

```bash
# Опит за пряк преход (гръмва) → правилният път минава
curl -X POST .../loan-applications/<ID>/transition -H "Authorization: Bearer <T>" \
  -H "Content-Type: application/json" -d '{"toStatus":"READY_FOR_BANK"}'

# Размяна на роли
curl -X POST .../loan-applications/<ID>/flip-borrower -H "Authorization: Bearer <T>" \
  -H "Content-Type: application/json" -d '{"familyMemberId":"<FM_ID>"}'
```
