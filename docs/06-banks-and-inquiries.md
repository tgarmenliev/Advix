# Фаза 6 — Банки и банкови запитвания

## Цел

Да свърже подготвената заявка с реалния пазар: база от банки и техните служители,
универсален шаблон за запитване, и изпращане на запитвания по имейл — с пълна
одитна следа какво точно е заминало.

## Какво включва

- **Банки** (`Bank`) с офиси (`BankOffice`) и служители за връзка (`BankContact`).
- **Шаблони за запитване** (`InquiryTemplate`) — универсален текст с placeholder-и.
- **Имейл услуга** с безопасен dry-run режим (Resend).
- **Банкови запитвания** (`BankInquiry`) — генериране, изпращане, snapshot, статус.

### Endpoints

| Метод | Път | Описание |
|---|---|---|
| POST/GET/PATCH | `/banks`, `/banks/:id` | Банки (писане: ADMIN) |
| POST/GET | `/banks/:bankId/offices` | Офиси на банка (писане: ADMIN) |
| POST | `/banks/:bankId/contacts` | Добавя контакт (ADMIN, CONSULTANT) |
| GET | `/bank-contacts` | Контакти с мек филтър по град |
| GET/PATCH/DELETE | `/bank-contacts/:id` | Контакт (писане: ADMIN, CONSULTANT) |
| POST/GET/PATCH/DELETE | `/inquiry-templates` | Шаблони (писане: ADMIN) |
| GET | `/inquiry-templates/default` | Шаблонът по подразбиране |
| GET | `/loan-applications/:id/inquiry-preview` | Преглед на попълненото запитване |
| POST | `/loan-applications/:id/inquiries` | Изпраща запитвания към избрани контакти |
| GET | `/loan-applications/:id/inquiries` | Запитванията по заявката |
| PATCH | `/bank-inquiries/:id/status` | Обновява статуса на запитване |

## Ключови решения (и защо)

### Имейл — безопасен режим по подразбиране
`EmailService` праща само ако има **реален** ключ и `EMAIL_DRY_RUN=false`. Иначе
работи в **dry-run**: логва писмото и връща синтетичен резултат, но нищо не
напуска машината.

**Защо:** запитванията отиват до реални банкови служители. По време на
разработка е недопустимо да се пращат истински имейли по случайност. Реалното
изпращане (през Resend HTTP API) се активира съзнателно, чак когато има ключ.

### Snapshot на изпратеното (одитна защита)
При изпращане текстът с попълнени placeholder-и се запечатва в
`BankInquiry.sentContent`. Дори администраторът да смени глобалния шаблон по-късно,
остава точен запис какво е заминало към конкретния служител.

### Универсален шаблон + placeholder-и
Един шаблон за всички банки; при ново запитване се взима маркираният
`isDefault=true`. Точно **един** default се пази — при маркиране на нов, старият
губи флага. Placeholder-ите (`{clientName}`, `{amount}`, `{bankName}`,
`{contactName}`, …) се попълват при изпращане; консултантът може да редактира
текста преди това.

### Мек филтър по град
Консултантът вижда по подразбиране контактите от **своя град** (през
`getCurrentUserCity`), но с `?allCities=true` или `?city=...` вижда останалите.
Филтърът подрежда, не заключва.

### Изпращането движи workflow-а
При изпращане на запитвания заявката преминава `READY_FOR_BANK → SENT_TO_BANKS`,
през същите правила по роля (PARTNER_A не праща; PARTNER_B иска одобрение от
ADMIN). Повторно изпращане е възможно и след `REJECTED_BY_BANK`.

## Правила и валидации

- Банки/офиси/шаблони: писане само ADMIN. Контакти: ADMIN + CONSULTANT. Четене:
  всички роли без CLIENT.
- Дублирано име на банка → `409`.
- Изпращане от статус, различен от `READY_FOR_BANK`/`REJECTED_BY_BANK`
  (и не вече `SENT_TO_BANKS`) → `400`.
- Липсващ default шаблон → `404` с ясно съобщение.

## Тестове

- Мек филтър по град (default / allCities / изричен град / консултант без град).
- Един default шаблон при маркиране.
- Placeholder заместване (познати/непознати).
- Имейл: dry-run по подразбиране; реален ключ → вика Resend.
- Изпращане: snapshot записан, преход извикан, dry-run резултат; липсващ контакт → `400`.

## Как да се провери

```bash
# Изпрати запитване (dry-run — нищо не тръгва реално)
curl -X POST .../loan-applications/<ID>/inquiries -H "Authorization: Bearer <T>" \
  -H "Content-Type: application/json" \
  -d '{"bankContactIds":["<CONTACT_ID>"],"consultantNote":"спешно"}'
```
В лога се появява ред `[DRY-RUN] Имейл до ...`, а заявката минава в `SENT_TO_BANKS`.

## Бележки за по-нататък

- `BankInquiry.status` подготвя следващата фаза (`BankOffer` — получени оферти).
- Обработката на грешки при имейл е best-effort: запитването се записва (snapshot),
  дори доставката да не успее.
